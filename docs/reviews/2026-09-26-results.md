## 1. Would binding Shopify fix the issues? Verdict

Shopify only resolves the parts it actually owns, and only once the app can reach it. Before this work the Shopify adapters were unreachable: `initializeDependencies()` was never called.

| Original finding | Fixed by Shopify alone? | Outcome |
|---|---|---|
| Tax, shipping rates, payment fields, billing address, order placement, order e-mail, checkout validation | **Yes.** The hosted Shopify checkout owns them. | In Shopify mode the app hands off to `checkoutUrl`. The local demo checkout is still correct but collects no card data. |
| Cart price tampering / stale prices | **Yes, in Shopify mode.** | Also fixed locally: the cart stores ids + quantities and re-prices from the catalog. |
| Stock truth, product photos | **Data yes, UI no.** | The domain now enforces stock and carries images; Shopify's CDN is allowed. |
| DI bootstrap never called | **No.** Shopify mode could not even be switched on. | The container is built lazily from env and fails fast on bad config. |
| Hardcoded product page data | **No.** The page never used the repository. | Pages load through use cases; unknown slugs return 404. |
| Product URLs | **No, it would break.** Shopify ids are GIDs. | `slug` = Shopify `handle`. |
| Ratings | **No, it would get worse** (0★ everywhere). | Ratings show only when real review data exists. |
| 99-item limit, filters, focus loss, counts, overflow, drawer a11y, 404 links, `&apos;`, fonts, language, consent, analytics events | **No.** All frontend/domain. | Fixed. |
| Shopify adapter bugs (new cart per change, ignored GraphQL errors, API 2024-01) | **No.** This is our client code. | Rewritten: line diffing, `userErrors`, API 2026-07, `@inContext(ES)`, pagination, caching. |
| Newsletter/contact delivery, server-side order tracking | **Backend.** | Left as documented backend work; the forms honestly say they are in demo mode. |

## 2. What changed

**Architecture.** The app now follows Clean Architecture end to end:
- Domain (`Money` in cents plus currency, `Product` with slug/images/details, `Cart` invariants on every path, `OrderPricing` policy).
- Application (use cases, ports for products, cart, checkout, orders, order-confirmation store, analytics, consent, newsletter and contact).
- Infrastructure (JSON catalog, localStorage cart, Shopify client and adapters, consent-gated PostHog, a lazily built and cached container).
- Presentation (design system, contexts, i18n).
- `app/` is Server Components first, using a `ProductSnapshot` for client islands. The dependency rule was verified by both independent reviews.

**UX.** The site is Spanish (es-ES, EUR). Changes by area:
- **Pages:** real product pages with metadata, JSON-LD, `notFound()` and related products.
- **Catalog:** filters are URL-synced and computed in memory, so inputs never unmount. Counts come from the full list.
- **Cart:** an accessible cart drawer with a focus trap, Escape and scroll lock. Quantities are bounded 1–99, mutations are serialised through a queue, and tabs stay in sync.
- **Checkout:** three steps with per-step validation, an error summary and focus management. It checks the postal code against the province and auto-fills the province, and ships only to the peninsula and Balearics (prices include IVA). The confirmation is rendered from a snapshot and survives a reload.
- **Content:** honest copy (no invented reviews, stats, team or claims), legal pages (privacy, cookies, terms, shipping/returns) and a GDPR consent banner where rejecting is as easy as accepting.
- **Accessibility:** zero axe WCAG 2.1 AA violations on every route and interactive state.

**Analytics.** PostHog loads only after consent, which also cuts shared JS from 199 kB to 103 kB. It is proxied first-party via `/ingest`.
- **Events:** a typed catalogue (product viewed, added/removed, cart viewed, checkout started, steps, order completed with revenue/tax, filters, forms).
- **Privacy:** no personal data in any payload, no `identify`, `ph-no-capture` on customer data and consent controls, and session recording and flags disabled.
- **Withdrawal:** stops the SDK completely (cookies on parent domains too).

**Engineering.**
- **Upgrades:** Next 15.5.26 and vitest 5; `npm audit` 0 vulnerabilities.
- **Tests:** 596 unit/component tests, including real-SDK PostHog tests, and 154 Playwright E2E tests on desktop and mobile.
- **CI:** lint, typecheck, test, build and E2E.
- **Headers:** CSP, HSTS and security headers.
- **Docs:** CLAUDE.md, README, ARCHITECTURE and `.env.example` rewritten against the code.

## 4. What remains (backend, infrastructure or business decisions)

1. **Newsletter and contact backend.** The adapters simulate delivery, and the forms say so. Connect an ESP/CRM by implementing `NewsletterService` / `ContactService`, then flip `isMessagingSimulated()`.
2. **Server-side purchase tracking.** Shopify orders complete on Shopify, so wire order webhooks to `posthog-node` for `order_completed`.
3. **Shopify admin configuration:**
   - shipping zones and rates matching `storePricingPolicy` (and excluding Canarias, Ceuta and Melilla);
   - a Spain market selling in EUR;
   - product images;
   - `productType` values for categories;
   - an optional reviews app (`reviews.rating` / `reviews.rating_count` metafields) and `custom.*` detail metafields.
4. **Before launch (legal):** set `NEXT_PUBLIC_CONTACT_EMAIL` and `NEXT_PUBLIC_LEGAL_NAME` / `_TAX_ID` / `_ADDRESS` (LSSI), and `NEXT_PUBLIC_SITE_URL`. Have the legal pages reviewed and the terms' commitments confirmed. Keep strike-through prices compliant with the EU/Spanish price-reduction rule (lowest price of the previous 30 days).
5. **Content:** photos for the accessories (they currently show a neutral placeholder).
6. **Maintenance:** keep the Shopify API version (default `2026-07`) inside Shopify's support window.
